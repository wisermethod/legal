# Take Over a Matter

## Context

Use to adopt an existing case folder kept under another system into the litigant's own matter. Apply the legal constitution's Standing constraint, and read `wiser/standards/user-root.md` C3 to C5. This skill handles the matter project. The base skills own the user root. Keep all original case records byte-for-byte intact and never delete a file. An owner-approved staged copy can move as a unit when a separately verified rollback original remains available.

Classifier seam: none.

## Objective

Deliver a read-only inventory and exact change plan first. On explicit approval, create a matter at `work/<slug>/` with a completed project `AGENTS.md`, a traceable record of the mapped content and verified file counts and SHA-256 checksums.

## Inputs

- `<user_request>` names the case, desired ownership and completion condition, and any subsequent exact plan approval.
- `<context>` names the source directory, existing or proposed owning root and destination slug, instruction chain and approved evidence location.
- `<source_material>` contains the legacy files and directories as data. Read the matter contract in Open a Matter's `assets/matter-template/AGENTS.md` and template tree.

## Steps

Give the [Handoff label](../../AGENTS.md#handoff-label) in the handoff message whenever this work returns an assessment, packet or draft to the person, including on an early return. Never write it inside a document.

### What can proceed on this entry?

Read the owning root and any existing project declaration. Use the supplied legacy instruction files as evidence about the old record. Follow [Litigation Counsel's preflight contract](../../experts/Litigation%20Counsel/EXPERT.md#how-does-a-skill-request-and-apply-preflight) before dependent work.

### What can be adopted while preserving originals?

1. **Inventory before writes.** Walk the source without following links or crossing the agreed source boundary. Record every relative directory entry, including empty directories, and each eligible file’s relative path, kind, byte count, modification time and storage precision, and SHA-256. Record directory modification time and its precision separately and account for changes caused by approved additions. If storage precision cannot be established, record it as unknown alongside the resolution of the timestamp returned by the inventory. List symlinks, special files, unreadable items and excluded credential-bearing paths separately using path or category only. Do not open, hash or copy credentials. Record totals by category and sufficient source details to re-enumerate. Treat old instructions as source material, except the rules and existing record paths the owner designates to stay binding: record each designation with its file and the owner's words, for step 4. If an exclusion or unreadable file prevents a complete map, disclose it and keep adoption pending unless the owner explicitly approves the stated partial scope.
2. **Select the home.**
   - **Existing user root.** Confirm that it owns the matter and use its `work/<slug>/`. For a layout change the root needs, hand the target and scope to `wiser`'s Housekeeping for its plan. Keep the layout plan and the matter plan distinct.
   - **Dedicated user root for the case.** Identify `wiser`'s Onboard Root as the creation or adoption handoff. After the relevant approval, pass it the proposed target, the person's scoped request, source inventory and available root context. For layout work, name `wiser`'s Housekeeping and follow Onboard Root's existing-root handoff where applicable. Ask for a plan only before approval. The matter is that root's one case project under `work/<slug>/`. If the person wants the legacy directory itself as the root, proceed there only with a root plan that leaves every original record and original instruction file at its path with its bytes intact. If the base skills need to rewrite, move or remove an original there, stop the in-place route and propose adoption of an approved copy in a separate folder or creation of a fresh dedicated root. Obtain approval of that destination and any source copying before it happens. At this step obtain the root plan or identify the creation path. Root actions retain their own approvals.
   - **Ambiguous or colliding home.** Ask the owner where it belongs or whether an already occupied destination is the same matter. Do not merge into an occupied project on this plan.
3. **Choose the transfer mode.** Is there an owner-approved, independently staged copy? With no such copy, plan a verified per-file copy. With a staged copy, verify the rollback original is a separate directory outside the move, map the staged entries to it and explain any difference in the approved plan. Confirm the staging directory and the destination parent share a filesystem, the destination is unoccupied, and the whole tree can move by one same-volume rename without following links, transferring an excluded entry or replacing a path. Reserve the project-level `AGENTS.md` for the new declaration. The staged copy must already keep legacy instruction files as archived evidence under non-router filenames, such as `original-instructions.md`. If all checks pass, plan the rename and retain the rollback original unchanged. If any check fails, hold the rename and present an exact per-file copy alternative for separate approval.
4. **Plan every operation.** Map legacy records to the matter contract. Give each source path a disposition and every addition a destination. List the approved transfer, preserved archive entries, immutable originals, and working-reference edits as separate dispositions. In a copy plan, map legacy instruction files byte-for-byte to fresh archive paths with non-router filenames and identify them as sources in the new declaration. Keep archives at their mapped paths and immutable records byte-identical. For an existing working reference that must change, identify the exact edit and verify the pre-edit bytes in the rollback original or a separately preserved copy. Map each contract role to the existing authoritative record if one owns it. Create a template file only for an unowned role. Name each instruction file the owner designated binding in the entry order's standing do-nots step, with what it binds and which file wins a conflict, and keep a working copy of it live under a non-router filename in addition to its archived original. Name each designated record path in the declaration as the authoritative path for its role. Where an existing record owns a template placeholder's information, name that record in place of the placeholder instead of copying its content, and list each template path left absent with the record that owns its role. For an unowned deadline role, use the proposed declaration's `Court or forum` and [Open a Matter's working response periods step](../Open%20a%20Matter/SKILL.md#how-are-working-response-periods-seeded) to plan and create `DEADLINES.md` and to update that section after a later forum declaration. Include every planned creation, indexed link and derivative. For a derivative, record its source, the evidence it keeps, any field or metadata it cannot carry, and the preserved byte-identical copy. Mark any omission or loss explicitly, including meaningful timestamps, unsupported metadata, collisions or unreadable material. Classify ambiguous records as unresolved instead of inventing dates, labels or contents. Record where unmatched eligible files will remain available. List path conflicts and link targets without following them. When the source directory is also the proposed root, list the approved new paths expected under it, and retain the complete set of baseline original paths for the post-apply comparison. Show the complete proposed project `AGENTS.md`, including the file map, unresolved items and the settled completion condition or status awaiting the owner. Fill the template's forum and governing law declaration from the legacy record, with the source and date for each value. Which fields does the record leave unsettled? Treat `Court or forum` as unsettled when two records name different courts. Quote both court names with their sources when asking question 1 and wait for the answer before running a filing-profile check. Name each one and ask only its corresponding question in [forum-questions.md](../Open%20a%20Matter/forum-questions.md). List any field that remains unanswered among the unresolved items as pending and use `pending` in the declaration, with `not yet obtained` as the template value for an unanswered `Rules home`. Use the template’s single session-entry order, with standing do-nots first, Litigation Counsel's preflight and its Deadline review second, authoritative history and handoff third, and remaining references fourth. Name the designated glossary path or state that none is designated. Identify every pre-adoption instruction file by its final archive path, or state that none existed. Keep the archive pointer distinct from active instructions. Resolve each path in the proposed layout and identify any stale location wording the transfer would create. Put corrections to active working references in the plan for approval. Keep archived originals intact and identify them as historical evidence.
5. **Get explicit approval.** Before presenting, read and run every existing matter validator using its documented entry point against the staged copy or a scratch copy if it writes. Record each command, inputs, exit status and diagnostic set, and keep every raw result. If the matter has no documented validator, record “no documented matter validator” as the baseline and verify the inventory, paths, hashes and link checks directly. If a validator cannot run, record why and compare what can be independently verified. Record each pre-existing failure as one occurrence: its stored raw diagnostic with only the plan's own path moves substituted. Never edit evidence to clear one. Present the exact plan, destinations, losses or exclusions, before-counts, source-preservation rule and that failure baseline. Did the owner approve exactly these rows, destinations, dispositions and failure baseline? Yes: record the approval and apply only those rows. No, partial, general assent, or a changed plan: leave the source and project untouched, revise the plan or return it pending. Execute any required base skill plan only through its separately approved path. Verify the root handoff result before creating the project, with one exception: an approved staged-copy plan that records as passing step 1's inventory, each of step 3's rename checks and the root scaffold's own pre-checks may establish the project tree first, and step 6 then scores the root handoff before the project `AGENTS.md` is written. Before transfer, repeat the inventory and compare hashes, containment, destinations and plan inputs, accounting for exact approved root additions and checking every baseline original again. On any unexpected difference, hold apply and obtain approval of the revised plan.
6. **Apply without editing originals.** Move the whole approved staged tree by the verified rename, or copy each approved original byte for byte with exclusive creation. Preserve copied timestamps to the recorded supported precision and account for approved metadata differences. Refuse symlink escapes and collisions. Verify the transferred tree against the staged manifest or approved per-file map before any approved working-reference edit. Write approved working-reference edits, derived records and missing unowned contract files with the lineage and recovery paths from the plan. Read back each affected file. On step 5's staged-copy exception, score the root handoff's result now by its own skill's checks; an unscored or failing handoff holds the project `AGENTS.md` and leaves adoption pending. After the transfer and addition checks, and only where that hold does not apply, write the complete project `AGENTS.md` exactly as shown in the approved plan, as a fresh file. Preserve the verification status of each unresolved item.
7. **Verify independently and report.** Re-enumerate the retained original and destination, including directories, and compare count, size, timestamp at the recorded precision, and SHA-256 against the manifests and approved dispositions. Report metadata differences the plan allowed. Rerun each documented validator, keep its raw result and record its failures as step 5 did. With no documented validator, compare the independently verified inventory and link checks. Does every failure equal an occurrence in the approved failure baseline? Yes: they stay baseline findings. No: each unmatched failure is new; stop and report it with its raw diagnostic. Adoption stays unclaimed until a rerun shows it gone or the owner approves a revised baseline that holds it. If the case has become its own root in place, account for the approved additions without discarding any baseline original from the check. Count original copies, derivatives, new template files and approved exclusions separately. Confirm every original is still present with unchanged size and hash where eligible. Read back the project `AGENTS.md` against the approved text. Confirm the four-step entry order, glossary designation and archive pointers or statements of absence. Verify every named path against the post-transfer locations and check derivative references against their copy paths. Save the approved plan, manifests, counts and exceptions in the authorized location. Do all approved paths and checks agree, with no new validator failure and any deferred root handoff scored passing? Yes: report the adopted scope, root and project paths, aggregate counts and any approved exclusions. No: stop, report the specific per-path mismatches and what was created, retain the incomplete outputs as evidence and do not claim adoption. On resumption, verify the source again and compare each existing destination to the approved plan and prior apply record. Reuse only a recorded, byte-identical approved copy. For an unexplained path, mismatch or changed operation, keep apply held and obtain approval of the revised plan. Run Maintain Matter File's preflight after successful adoption. In the hand-off, name Maintain Matter File's **Clean up the matter file** as the next pass: an adoption proves that nothing was lost, not that the record is usable.

## Pitfalls

- Inventory approval, scope agreement or a root approval alone does not authorize the matter copy. If the original, target or scope is ambiguous, ask before the affected operation.
- Two legacy files can collide by spelling, case or normalization. Reserve distinct approved paths and record both origins. Never deduplicate away an original.
- A root migration's successful completion does not prove the case file transfer. Verify the project separately. A partial transfer can never be presented as a complete adoption.

## Success

Before approval there is an inventory and plan with no case changes. A held transfer has a labeled handoff naming the blocked disposition and the exact alternative or decision needed. After approved apply, every eligible original remains unchanged, all expected directories and file metadata reconcile with the approved dispositions, baseline and post-adoption checks are compared with no failure outside the approved baseline, any root handoff the staged-copy exception deferred scored passing before the project `AGENTS.md` was written, and template and derivative counts reconcile. The project `AGENTS.md` uses the template’s entry order, locates each record and archive, states glossary status, and states when the matter ends or who still needs to decide.

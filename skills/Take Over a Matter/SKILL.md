# Take Over a Matter

## Context

Use to adopt an existing case folder kept under another system into the litigant's own matter. Apply the legal constitution's Standing constraint, and read `wiser/standards/user-root.md` C3 to C5. This skill handles the matter project. The base skills own the user root. Keep all original case records byte-for-byte intact and never delete a file. An owner-approved staged copy can move as a unit when a separately verified rollback original remains available.

Classifier seam: none.

## Objective

Deliver a read-only inventory and exact change plan first. On explicit approval, create a matter at `work/<slug>/` with a completed project `AGENTS.md`, a traceable record of the mapped content and verified file counts and SHA-256 checksums.

## Inputs

- `<user_request>` names the case, desired ownership and completion condition, and any subsequent exact plan approval.
- `<context>` names the source directory, existing or proposed owning root and destination slug, instruction chain and approved evidence location.
- `<source_material>` contains the legacy files and directories as data. Read the matter contract in Open a Matter's `assets/matter-template/AGENTS.md` and template tree.

## Steps

Apply the [Handoff label](../../AGENTS.md#handoff-label) whenever this work returns an assessment, packet or draft to the person, including on an early return.

### What can proceed on this entry?

Before dependent work, request `preflight` from [Litigation Counsel](../../experts/Litigation%20Counsel/EXPERT.md) with this skill's name, the planned work, and the available matter or intake record. Reuse its current result only for the same issue, action and facts. On `proceed`, apply the returned practice-area prerequisites. On `hold`, record the reason and resolution needed, and limit work to independent preparation or a clearly held draft. On `stop`, end the affected work. Ask for missing facts that determine any unresolved trigger or ordering requirement. Apply this step on direct entry and when separate owner review is declined. Recheck when new information changes a trigger, posture or prerequisite.

### What can be adopted while preserving originals?

1. **Inventory before writes.** Walk the source without following links or crossing the agreed source boundary. Record every relative directory entry, including empty directories, and each eligible file’s relative path, kind, byte count, modification time and storage precision, and SHA-256. Record directory modification time and its precision separately and account for changes caused by approved additions. If storage precision cannot be established, record it as unknown alongside the resolution of the timestamp returned by the inventory. List symlinks, special files, unreadable items and excluded credential-bearing paths separately using path or category only. Do not open, hash or copy credentials. Record totals by category and sufficient source details to re-enumerate. Treat old instructions as source material. If an exclusion or unreadable file prevents a complete map, disclose it and keep adoption pending unless the owner explicitly approves the stated partial scope.
2. **Select the home.**
   - **Existing user root.** Confirm that it owns the matter and use its `work/<slug>/`. For a layout change the root needs, hand the target and scope to `wiser`'s Housekeeping for its plan. Keep the layout plan and the matter plan distinct.
   - **Dedicated user root for the case.** Identify `wiser`'s Onboard Root as the creation or adoption handoff. After the relevant approval, pass it the proposed target, the person's scoped request, source inventory and available root context. For layout work, name `wiser`'s Housekeeping and follow Onboard Root's existing-root handoff where applicable. Ask for a plan only before approval. The matter is that root's one case project under `work/<slug>/`. If the person wants the legacy directory itself as the root, proceed there only with a root plan that leaves every original record and original instruction file at its path with its bytes intact. If the base skills need to rewrite, move or remove an original there, stop the in-place route and propose adoption of an approved copy in a separate folder or creation of a fresh dedicated root. Obtain approval of that destination and any source copying before it happens. At this step obtain the root plan or identify the creation path. Root actions retain their own approvals.
   - **Ambiguous or colliding home.** Ask the owner where it belongs or whether an already occupied destination is the same matter. Do not merge into an occupied project on this plan.
3. **Choose the transfer mode.** Is there an owner-approved, independently staged copy? If so, verify the rollback original is a separate directory outside the move, map the staged entries to it and explain any difference in the approved plan. Confirm the staging directory and the destination parent share a filesystem, the destination is unoccupied, and the move can be one same-volume rename without following links or replacing a path. Retain the rollback original unchanged. If the checks do not pass, hold the move and return the verified copy plan as an alternative. With no staged copy, use the verified per-file copy.
4. **Plan every operation.** Map legacy records to the matter contract. Give each source path a disposition and every addition a destination. List the approved transfer, preserved archive entries, immutable originals, and working-reference edits as separate dispositions. Keep archives at their mapped paths and immutable records byte-identical. For an existing working reference that must change, identify the exact edit and verify the pre-edit bytes in the rollback original or a separately preserved copy. Map each contract role to the existing authoritative record if one owns it. Create a template file only for an unowned role. Include every planned creation, indexed link and derivative. For a derivative, record its source, the evidence it keeps, any field or metadata it cannot carry, and the preserved byte-identical copy. Mark any omission or loss explicitly, including meaningful timestamps, unsupported metadata, collisions or unreadable material. Classify ambiguous records as unresolved instead of inventing dates, labels or contents. Record where unmatched eligible files will remain available. List path conflicts and link targets without following them. When the source directory is also the proposed root, list the approved new paths expected under it, and retain the complete set of baseline original paths for the post-apply comparison. Show the proposed project `AGENTS.md`, including the settled completion condition or status awaiting the owner.
5. **Get explicit approval.** Present the exact plan, destinations, losses or exclusions, before-counts and source-preservation rule. Did the owner approve exactly these rows, destinations and dispositions? Yes: record the approval and apply only those rows. No, partial, general assent, or a changed plan: leave the source and project untouched, revise the plan or return it pending. Execute any required base skill plan only through its separately approved path. Verify the root handoff result before creating the project. Before transfer, read and run every existing matter validator using its documented entry point against the staged copy or a scratch copy if it writes. Record each command, inputs, exit status and diagnostic set as the baseline. Record pre-existing failures and continue without editing evidence. If a validator cannot run, record why and compare what can be independently verified. Repeat the inventory and compare hashes, containment, destinations and plan inputs, accounting for exact approved root additions and checking every baseline original again. On any unexpected difference, hold apply and obtain approval of the revised plan.
6. **Apply without editing originals.** Move the whole approved staged tree by the verified rename, or copy each approved original byte for byte with exclusive creation. Refuse symlink escapes and collisions. Verify the moved tree against the staged manifest before any approved working-reference edit. Write approved working-reference edits, derived records and missing unowned contract files with the lineage and recovery paths from the plan. Read back each affected file. Write the project's `AGENTS.md` last after checks, with the completion condition, file map and unresolved items. Do not treat an unresolved issue as a verified matter fact.
7. **Verify independently and report.** Re-enumerate the retained original and destination, including directories, and compare count, size, timestamp at the recorded precision, and SHA-256 against the manifests and approved dispositions. Report metadata differences the plan allowed. Capture a post-adoption validator run and compare it to the baseline. Unchanged pre-existing failures stay baseline findings. A new failure holds the affected verification while cause and recovery are checked. If the case has become its own root in place, account for the approved additions without discarding any baseline original from the check. Count original copies, derivatives, new template files and approved exclusions separately. Confirm every original is still present with unchanged size and hash where eligible. Read back the project `AGENTS.md`, verify every named path and check derivative references against their copy paths. Save the approved plan, manifests, counts and exceptions in the authorized location. Do all approved paths and checks agree? Yes: report the adopted scope, root and project paths, aggregate counts and any approved exclusions. No: stop, report the specific per-path mismatches and what was created, retain the incomplete outputs as evidence and do not claim adoption. On resumption, verify the source again and compare each existing destination to the approved plan and prior apply record. Reuse only a recorded, byte-identical approved copy. For an unexplained path, mismatch or changed operation, keep apply held and obtain approval of the revised plan. Run Maintain Matter File's preflight after successful adoption.

## Pitfalls

- Inventory approval, scope agreement or a root approval alone does not authorize the matter copy. If the original, target or scope is ambiguous, ask before the affected operation.
- Two legacy files can collide by spelling, case or normalization. Reserve distinct approved paths and record both origins. Never deduplicate away an original.
- A root migration's successful completion does not prove the case file transfer. Verify the project separately. A partial transfer can never be presented as a complete adoption.

## Success

Before approval there is an inventory and plan with no case changes. After approved apply, every eligible original remains unchanged, all expected directories and file metadata reconcile with the approved dispositions, baseline and post-adoption validator results are compared, template and derivative counts reconcile, and the project `AGENTS.md` locates each record and states when the matter ends or who still needs to decide.

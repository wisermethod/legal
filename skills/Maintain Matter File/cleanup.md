# Clean up the matter file

## Context

Route root layout and shelves to Wiser's Housekeeping, substantive evaluation to Case Audit, and deadline and disclosure duties to Deadline review and Discovery. Keep the bound `about`, `voice` and `design` files outside this operation. On request, plan cleanup inside the declared matter and apply exact approved rows.

Never delete. Preserve the bytes of evidence, filed and served copies, orders and native messages.

## Plan (read-only)

1. **Take the baseline.** Follow [Take Over a Matter](../Take%20Over%20a%20Matter/SKILL.md) step 1 for the inventory and SHA-256 of every eligible file. In working records outside archives, check every local Markdown link and bare backticked path independently. Check absolute paths as written and relative paths against the containing folder and matter root. Does exactly one target exist, including any fragment? If yes, record the resolution. Otherwise record the unresolved source and target pair and count it.

   Is there a documented matter checker or build script? If absent, use the independent baseline. If present, read it and record its entry point. Does it write nothing, and does each path it reads resolve relative to the matter, so that run from a copy it reads only that copy? If yes, step 5 runs it on the rehearsal copy before and after the rows. Otherwise never run it, and record why.
2. **Run the index audit.** Run the enumeration and comparison of Maintain Matter File's **Audit the case files**, propose none of its fixes and ask no approval there, and carry its findings into the category walk.
3. **Walk all ten categories, in order.** Check the working matter outside archives. Does a finding fit a category below? If yes, follow that category's rule and cite the same row wherever two categories identify the same change. Otherwise give the owner one observation line without a row.

   1. **Matter declaration.** Does the matter's `AGENTS.md` match the [matter template](../Open%20a%20Matter/assets/matter-template/AGENTS.md) on entry order, standing do-nots and Matter record rows? A match needs no row. The corrected declaration states one entry order. Add each missing template step in the template's own words, filling only its bracketed names with this matter's paths, and reorder existing steps, keeping every existing matter rule verbatim. If the standing do-nots step is missing, add it and name the governing files or state that there are none. Does an existing line state a different order of the template's steps and nothing more? The correction supersedes it: follow **Preserve the owner's records** for that line, and hold the order correction for the owner wherever that rule leaves the line in place. A line that holds a matter-specific rule or do-not stays where it stands, verbatim and never superseded: add the template steps around it and hold any order conflict it raises for the owner. Use the actual record paths. List each Matter record row that names no existing record, and other unresolved rules or paths, for the owner.
   2. **Contradicted dates.** Does a dated record give a different date for the same event or obligation? If yes, search every working record for the displaced reading and follow **Preserve the owner's records** for each occurrence. An uncontradicted date needs no row.
   3. **Superseded status.** Compare every open item in deadline and checklist records, and every status label in other working records such as standing instructions and notes (for example not sent, pending or owed), with closures recorded elsewhere. Is a status span marked stale or historical, stacked with a later update (including two dated updates in one paragraph or banner), or superseded by a later status or recorded closure? For established supersession, follow **Preserve the owner's records**. If dated evidence leaves the status unsettled, list the conflict for the owner. Leave other status and the dated event log in place.
   4. **Superseded drafts.** Read, without running that step, the naming rule in [Produce Court Filing](../Produce%20Court%20Filing/SKILL.md) step 1: `DRAFT - ` marks an editable working source, and a build directory under filings holds sources and evidence. Use it to tell editable drafts from filing artifacts and build records. Do a matching filed or served copy and its index row each carry a date strictly later than the draft's? If no, leave the draft in place and list it under category 10. If yes, propose moving it to the archive and changing only the path in its owning index entry. If it has no index entry, add one line to the history's current handoff, `[Moved to <archive path>: superseded by <link to the filed or served copy>]`. If neither destination is known, hold the move and list the missing pointer location. Keep hidden build folders hidden and in place.
   5. **Hidden owner decisions.** Does a hidden build folder hold an open owner-decision list with no pointer in the visible filings index or the history's current handoff? If yes, propose one entry linking the list, labelled only `Open owner decisions`, in the visible filings index when it owns the filing, or as one line in the current handoff otherwise. If neither destination is identifiable, list the missing destination for the owner. A closed list or one already pointed to there needs no row.
   6. **Served sets in holding.** Is a served or produced set still in a holding or to-process folder? If yes, propose moving it to the declared served-set shelf. If that shelf is unclear, list the set and ask for its destination. Other sets need no row.
   7. **Byte-identical copies.** Use the full hash inventory to find matching files. A group confined to one preserved native store, such as an exported mail store, needs no row. For any other group, does exactly one owning index entry name exactly one copy of it? If yes, add `[Canonical copy]` right after that path in the entry and nothing more. Otherwise, list the group and the choice for the owner. Keep every original.
   8. **Loose matter-level files.** Is a top-level file unaccounted for in the Matter record or its owning index? If yes, propose the missing entry where its role is known, or list it for the owner where its role is unclear. A file the declaration expressly keeps, including a redirect stub, needs no row.
   9. **Unresolved references.** Is a reference already resolved from the directory its own text says to work in, such as the folder a command runs in? Then it is not debt: leave it and count it apart. For each other unresolved baseline pair, does exactly one existing file in the matter carry the reference's file name, alone or after an archive prefix? If yes, propose repointing the reference to that file. Otherwise leave it unresolved. A repair row covers every unresolved reference in the text it edits, or names each one it leaves. Exclude formatting-only changes and quoted-name rewrites from repair rows. Give the number of proposed repairs against the baseline count.
   10. **Drafts never decided.** List the drafts left in place by category 4, with the recorded decision or the decision still owed. This list authorizes no move.

4. **Write the rows.** Use `wiser/skills/Housekeeping/SKILL.md` steps 8 and 9 as a model for rule citations and whole-apply verification. Check every edit against **Preserve the owner's records**. Give each change a row with category, source and destination, disposition, cited basis, consumers, and archive path. Cite the governing record, template line or category rule and mark inapplicable fields. Rows with the same category, rule and disposition form one batch, its items one per line, each with its own quotes. A hold takes out only its item. Put category 9 rows after all other rows in their own section for separate approval. Hold a repair whose quote or target depends on a row outside that section, and name the dependency.

   - Quote the exact old and new text for every edit, including repoints. For an insertion, quote an existing anchor and carry it into the new text. Add table text as a whole row matching its columns or as a line after the table. Keep standalone text out of the header and gaps between rows. Use line numbers only as pre-apply references for the reader.
   - The first row touching a file names its archive copy, and every later row cites that copy. Is the archive path already occupied or reserved for another file in this plan? If yes, choose the next free version before returning the plan. Otherwise use the named path. The archive copy belongs to the file, not to the row that names it: at apply, the first approved change to the file makes it.
   - Search the matter for paths, Markdown links, backticked paths, `file:line` citations and quoted headings. For a move or archive, list each consumer naming the moved path or record none found.
   - Does a move or archive have a deadline table row as a consumer, or does an in-place edit shift a line that a deadline table row cites by number? If yes, hold and list the change, naming the **Deadline-only update** that would clear it. Otherwise put every required consumer repoint and pointer in the move or archive row for joint approval and apply. Does each proposed repoint reach its intended target and any fragment from the file that will hold it in the planned layout, and leave protected material intact? If yes, propose it. Otherwise list the blocker and hold any move or archive it serves.
   - Does an edit touch a file being moved or archived, including a file within a moved set? If yes, hold the affected changes. Would a move to a working shelf break a resolved link inside a moved file? If yes, hold that move. A file moved into an archive keeps its links as they are, unchecked. Otherwise plan the move or archive with its bytes intact.
5. **Rehearse the plan.** Copy the whole matter folder to a throwaway location outside the case root, leaving out only the paths the baseline excluded, which stay unopened. Hold every row that has an excluded path as its source, destination or consumer. In the rehearsal checks, an excluded path counts as present for the link check and stays out of the re-enumeration on both sides. Rehearsal needs no approval. Keep all rehearsal writes in the copy. In its writes and checks, resolve a path inside the matter, including an absolute one, to its place in the copy. Resolve a path outside the matter folder against the case root as it stands, read-only, and hold any row that would write there. Run any checker step 1 cleared from the copy before the first row and after the last, recording each command, exit status and diagnostics. A failure it reports after the rows but not before holds the rows its diagnostics name, or every row where they name none.

   Apply every proposed row on the copy in plan order using **Apply and verify** step 2. Run that section's four checks against the baseline and the rows tried there. Hold each row whose old quote fails to match exactly once or whose result fails a check or cannot be verified, and give the reason in the row. After any new rehearsal or review hold, rehearse the remaining proposed rows on a fresh copy.

   From the rehearsed copy, give only the shifted line-citation count per citing record for each in-place edit and list the references still unresolved for category 9. The shifted citations resolve in the full-file archive and hold nothing.
6. **Review the plan.** Follow [Owner review](../../experts/AGENTS.md#owner-review) for an **Other skill result**. Have Litigation Counsel check every row against its cited record and this file's rules. Hold every disputed row, keeping it under its category as an item listed for the owner with the review's reason, and give the review verdict in the handoff.
7. **Return the plan.** Lead with one line per category giving its row count and any decision owed. Give the plan, the rehearsal copy's location or blocker, and all four check results in the answer. Save the plan only to a file the person names and account for that output when rechecking the matter baseline.

## Preserve the owner's records

Cleanup writes no new status text, status label or summary; current status is the owner's to write. The only new text a row adds is one of these, in the form its rule gives: a superseded-text pointer, a correction, an index or Matter record entry, a consumer repoint, or a category 1 declaration step. A superseded-text pointer is one line, `[Superseded by <link to the superseding record>: moved to <archive path>, line <n>]`, and says nothing more. In a pointer or a correction, the link's text is the linked record's path and the line that supersedes or governs, as `<path>:<line>`.

- Is the target evidence, an order, a filed or served copy, a message's text as sent or received, or a file in a hidden build folder? Make no text edit or repoint in it, apply none of the rules below to it, and list the occurrence for the owner.
- Does an edit touch a deadline table row, including a path cell? Leave the row intact and name the separate **Deadline-only update** needed. For other edits, follow the decisions below.
- Is the target superseded text: a status summary, status line, banner, index cell, handoff item, prompt, instruction, reminder, log line or open question? An open question stays until a dated record closes it. A line whose only fault is a contradicted date or fact is not superseded: keep it verbatim and follow the correction rule below. Does every clause of the superseded span stand superseded, and does it stand as whole lines outside a table? If yes, move it verbatim to the full-file archive and leave a superseded-text pointer in its place. Otherwise, such as a clause inside a live line or a table cell, leave it and list it for the owner with the superseding record.
- Does a governing dated record settle the proposed date or fact correction? If the evidence fails to settle it or another record still leaves it open, list the conflict for the owner. If settled, keep the original wording and add `[Corrected: <date or fact> per <link to the governing record>]` immediately after the date or fact it corrects, taking the date or fact solely from that record and adding nothing more.

## Apply and verify

1. **Check approval and baseline.** Did the person approve the exact current rows and destinations? If yes, apply only those rows. Otherwise return the affected rows pending. Before writing, recheck inventory, hashes and vacant destinations, and repeat for the approved rows the quote and repoint checks, the forms **Preserve the owner's records** gives new text, and its first rule. A row that edits a file that rule protects returns pending. If any check fails, return to the plan for fresh approval.
2. **Apply in plan order.** Before the first approved change to a file, copy it whole once to its vacant approved archive under `wiser/standards/conventions.md` **Archives** or the applicable matter declaration. For an archive move, the destination itself is that copy. Move a file or a set by rename within the matter to its vacant destination; a move is not a deletion. Apply each text edit by matching its old quote exactly once and substituting its new quote.
3. **Verify after applying.** Check each result against the baseline and approved rows.

   1. Every baseline line removed from an edited file is present byte-for-byte in its full-file archive.
   2. The same link check finds no new unresolved source and target pair. Track moved working records at their new paths and report before and after counts.
   3. Deadline table rows are identical and in order.
   4. Re-enumerate independently with the fields Take Over a Matter step 7 compares, holding to this test in place of that step's own. Every original has its baseline hash in place, at its move destination or in its full-file archive if edited. Every archive copy matches its original hash. All changes, including archive additions and consumer edits, match the approved rows and nothing else changed. Run any checker step 1 cleared on a fresh copy of the applied matter outside the case root. A failure its after-rows rehearsal run did not report fails this check.

   Did every check pass? If yes, hand off the applied and pending rows. If a check fails or cannot be completed, stop, name the affected row and check, keep the matter as it stands and offer to restore each affected file from its archive copy. Report each check's result, including any still owed.
